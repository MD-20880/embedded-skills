# 工程主线、决策与代码追溯

## 1. 一个项目的几个关键入口

`外部事实与约束 → 系统方案 → 协议/工程契约 → 实现方案 → 代码与验收`。

- ADR 横向连接重要取舍，解释“为什么不是另一种合理方案”；不是所有决定都需要经过 ADR。
- Issue 收集用户反馈、问题和工作假设；可以触发修改任何主线节点，不能自动批准主线变更。
- 多个基础设施版本和应用实现可并存，但必须标明受哪个契约版本约束。
- 验证结果与新证据可以推翻上游假设，必须评估适用范围并经过相应审核。

“导航不超过三层”是目标：从主题入口进入协议/方案，再定位组件与测试；不限制源码真实依赖深度。深层细节一旦改变上层行为、兼容或安全承诺，就需要向上报告。

## 2. ADR 何时需要

不用“讨论耗时”或“跨几个文件”衡量重要性。问：

1. 新工程师只看当前规范和代码，是否会合理问“为什么拒绝另一条看似可行的路线”？
2. 别的团队/Agent 如果任意推翻此选项，是否会破坏他们已依赖的共同前提、产品能力边界或不可逆交付？

通常值得 ADR：硬件型号与接口布局、出货后的可维护性、Bootloader 持久数据兼容、跨板协议版本路线、长期资源所有权、重大风险/性能取舍。

通常不值得 ADR：局部重构、临时 DMA 实验、测试用的帧大小、普通错误处理实现、已在规范清楚确定的字段细节。它们应留在 Issue、PR、配置或方案中。

一项选择被多人依赖时，先建立**适用范围和版本化承诺**；若还涉及需长期解释的非显然取舍，再交给 ADR。被接受的 ADR 用新记录取代，不直接覆写理由。试验中经常变更的想法不能被伪装为 Accepted。

## 3. 从代码到依据、从依据到影响

`外部依据 → 工程条款（稳定 ID 可选） → Component/Board/Program → Firmware Target → Test/实板证据`。

- 普通源码通过唯一归属的组件间接连到契约；不要给每个函数手写同一文档 ID。
- 通信线格式、安全关断、非易失记录布局和共享 DMA/I²C 归属等关键约束，可在模块或测试中引用条款 ID。
- 实际源码→编译目标关系从 CMake/构建系统获取；不同 Target 的编译参数、MCU 和配置不可混淆。
- 强制条款如无实现、实现无验证、或实现依据已被取代，应生成可操作的缺口问题；AI 推断关联只能标为候选。
- 变更上游文件时，反向列出消费者、需复核的 Build/Test 和外部验收证据，并注明“不受影响”的证据边界。

## 4. 处理 Transform 和并发 Agent

变更分为三类：

| 变更 | 处理 |
| --- | --- |
| 仅改变内部实现，公开行为不变 | 在原契约与任务边界内修改、补最小保护测试 |
| 修改行为契约或跨板职责 | 提议新修订，列受影响消费者、兼容期和验证；授权后更新共同基线 |
| 修改外部事实、硬件/法律限制或重大决策 | 保留原始证据，重新评估方案/ADR/协议，识别过时任务并更新各 Agent 约束 |

Agent 任务至少记录：目标、受影响对象、基线（commit/协议版本/硬件）、允许范围、不可改的契约、验证证据和越界时的升级条件。任务结束时把新的当前规则写回归属文档/代码/测试，不把聊天记录作为交接唯一材料。

## 5. 有界诊断

出现故障时，接手者应从单一当前入口尽快查到：适用版本、现象与复现条件、模块责任、观察证据、现行契约和下一项有效实验。历史 PR 与实验报告是核查资料，不是必须从头阅读的教程。

对硬件异常，明确区分资料推理、主机测试、台架实测、整机验证与第三方认证；采用项目的证据等级规则（如 L0–L4）并保留实物/固件版本。不得保证所有间歇性故障都在固定时间内解决；如果缺关键测量，应给出最有区分力的下一步而非堆砌猜测。
