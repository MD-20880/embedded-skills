# 工程知识与文档治理（knowledge-governance）

让新接手的人或 AI 从少量**当前有效的工程契约**进入项目，在有限阅读深度内找到受约束的实现、验收和历史理由。产出**带来源的现状盘点、权威性冲突列表、分类/迁移提案及维护规则**。不自动把草案批准为正式规范，也不负责实际撰写 ADR、协议或关闭 Issue。

方法细节按需读取：
- [文档分类与状态](references/document-classes.md)
- [工程主线、变更与代码追溯](references/decision-trace.md)
- [可选的项目治理文档模板](assets/knowledge-governance-template.md)

## 输入与产出

| 项 | 说明 |
| --- | --- |
| 输入 | 项目文档索引、各文档头部与状态、协议/方案、ADR、Issue、原理图/Datasheet 元数据、代码及构建/测试事实；用户的范围与目标 |
| 默认产出 | 回复中的文档分类表、当前权威入口、冲突/过期清单、建议目录或索引调整、可独立执行的迁移与复核步骤 |
| 用户明确要求落地时 | 经确认的项目专用治理说明、目录索引/链接修订或 PR；项目事实放项目仓库，不写入本 Skill |
| 不产出 | 自动接受 ADR、修改协议行为、替测试作验收、从文件名臆测硬件事实 |

## 流程

### 1. 读取项目画像

1. **读取项目画像**：读取项目根目录 `docs/embedded-profile.md`。
   - 存在：以其中事实为准；只读取本任务需要的第 1（项目阶段）、5（目录）、8（文档）、9（已知约束）节；必要时查第 2 节硬件版本。若发现画像与代码不一致，以代码为准，并在结尾提示用户运行 `/emb-repo:project-profile update`。
   - 不存在：按需最小化探索仓库获取本任务所需事实，并在结尾建议用户运行 `/emb-repo:project-profile` 建立画像。不要因为缺少画像而中止任务。
2. 读取仓库当前的文档索引、ADR 目录配置/规则、文档状态约定和模块 README。只追溯本任务涉及的来源，不必通读全部长协议。
3. 记录用户规定的不可修改区域、外部资料版权/只读限制及预期输出路径。没有明确迁移授权时只审计、给提案。

### 2. 按角色和生命周期盘点

1. 列出项目相关文档，先按 [document-classes.md](references/document-classes.md) 分为：**外部依据、需求、系统方案、协议/工程契约、实现方案、ADR、Issue/问题、验证计划、原始证据/记录、历史/实验、模块使用说明、索引**。
2. 每份文档记录：路径、角色、文档标识/版本、状态、适用硬件/产品范围、来源与当前消费者；缺失填“未知/待确认”，不要用最近修改时间猜“有效”。
3. 区分**批准的规范**、**未批准的目标设计**、**历史 Demo 的实际接口**和**已验收的产品行为**。它们可能同时存在，不得仅因文件放在 `docs/` 根目录而认定为权威。
4. 找出混杂和漂移：多份自称 SSOT、旧链接指向新规范、原始实验和正式规范混排、未记录版本、同一行为在两处定义、草案被下游当作 Accepted。附具体文件证据。

### 3. 建立当前工程主线

1. 用 **外部依据/需求 → 系统方案 → 当前协议/工程契约 → 实现方案与代码 → 验证计划与结果** 展示主线；重大非显然取舍以 ADR 解释“为什么”，不是必经审批层。参见 [decision-trace.md](references/decision-trace.md)。
2. 为每一个受管理主题选择**一个当前入口**；可能是工程规范、模块 README 或项目索引。入口必须说明权威状态、版本、适用对象、实现入口、验证入口和历史链接。一个入口可以指向多个分工明确的协议，不强行合并长文档。
3. 规划从当前规范到代码的**分层追溯**：文档或稳定条款 ID → Board/Component/Program → CMake Target → 测试与验证记录。确定性的源码→Target 关系由构建信息生成，不人工复制维护；关键安全/兼容条款可单独建立精确引用。
4. 分开表示：**规范状态**（草案/已批准/已取代）、**代码实现状态**（未实现/部分/已实现）、**验证状态**（未执行/通过/失败）。不要把“写在主分支”与三种状态画等号。

### 4. 给出最小改动的分类与迁移方案

1. **先分类和建立索引，再考虑移动目录**。可选的类别化目录见 [document-classes.md](references/document-classes.md)，不要强行套到用户现有工程。
2. 对每份需要处理的文档给出动作：保留原位并标状态、添加入口链接、合并重复叙述、移到历史/记录、停止更新、或提出规范修订。对每项说明依据、消费者、链接风险及回退方式。
3. 旧源码、历史记录、厂商 PDF、原理图应优先原样保留并使用稳定哈希/来源索引；不要把外部原始资料重写为“内部规范”。
4. 设计旧路径的链接兼容方案（重定向说明/保留索引/引用改写），并列出不可一次迁移的工作。不为了目录整洁同时修改产品行为。

### 5. 为 AI 和人类建立决策与冲突边界

1. **工作假设**留在 Issue/实验/PR；**当前可依赖的行为**写入版本化方案/协议；**需要长期解释的跨边界取舍**才建议 ADR。判定问题与例外见 [decision-trace.md](references/decision-trace.md)。
2. 新证据与当前契约冲突时，列明：事实/推断、适用版本、受影响的消费者、缺少的验证、需要谁确认。不得由 AI 静默更改已批准的规范或将未测试的结果写成通过。
3. 需要起草/取代 ADR 时转交 `/emb-design:adr-write`；Issue 分类、关闭和证据等级交给 `/emb-project:issue-tracking`；协议行为编写交给 `/emb-docs:protocol-spec`（如已安装/可用）；仓库索引同步交给 `/emb-repo:docs-index-sync`（如已安装/可用）。本 Skill 仅协调分类、关系与迁移提案。
4. 呈现“当前诊断入口”：现象、配置和硬件版本、有效契约、责任模块、关键证据和下一项区分性实验；不要求接手者先读几十个旧 PR 或聊天记录。

### 6. 自检与汇报

- [ ] 每项“权威”判断都有状态/版本/来源；草案或旧 Demo 未冒充产品规范。
- [ ] 外部资料与原始验证证据保留来源，未虚构数值、根因或验收。
- [ ] 分类表覆盖受审范围，每项拟移动文件有具体理由和断链处理。
- [ ] Issue、ADR、协议、方案、源码、测试没有重复定义同一份权威事实。
- [ ] ADR 与工程承诺的门槛清晰，短暂工作假设不会产生决策记录泛滥。
- [ ] 提案指出需要人确认的规范状态、版本范围及高风险迁移。
- [ ] 从当前入口可在有限的导航步骤内定位负责模块与验证；深层历史只用于核查证据。

输出顺序：**当前判断 → 文档权威性/类别表 → 建议入口图 → 冲突与待确认 → 最小迁移批次 → 验证与回退**。没有用户明确许可时只输出建议，不改动项目目录、权威文档或 Issue。

## 约束

- Skill 是跨项目通用方法，禁止嵌入特定产品板号、引脚、仓库绝对路径或未确认的项目事实。
- 目录与文件的放置**不决定权威性**；版本、审批状态与适用范围才决定。
- 可检索的历史不等于当前有效约束；向量相似/AI 猜测不等于已证实的引用或合规结论。
- 用户要求保留项目特定内容时，尊重指定位置；未授权不复制本 Skill 的整套方法论到项目仓库。
- 禁止为整理文档而擅自关闭 Issue、接受 ADR、合并 PR、移动硬件原始资料或改变协议。
