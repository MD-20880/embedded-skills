# MCU 引脚资料格式与来源规则

## 1. 交付物与元数据

每个板卡版本、每个 MCU 位号一份 Markdown。路径遵循项目约定；无约定时用 `docs/hardware/<board>/<revision>/<mcu-ref>-pin-map.md`。正文按外设组织，不把所有源文件和长引脚表塞进项目画像。

文件头使用 `---` 包裹的 **JSON 对象**：它是合法 YAML 的子集，也能用 Python 标准库严格读取，避免额外依赖或自制 YAML 解析器。本版不接受任意 YAML 写法；不要手工改写机器元数据。以下仅演示结构，摘要由脚本填写：

```yaml
---
{
  "schema": "mcu-pin-map/v1",
  "target": {
    "board": "example-board",
    "revision": "rev-a",
    "mcu_ref": "U1"
  },
  "source_binding": {
    "hash_policy": "sha256-text-lf-binary-raw-v1",
    "inputs": [
      {
        "path": "hardware/example-board/rev-a.net",
        "hash_mode": "text-lf",
        "sha256": "<脚本计算的64位小写十六进制摘要>"
      }
    ]
  }
}
---
```

| 字段 | 约束 |
| --- | --- |
| `schema` | 固定为 `mcu-pin-map/v1`；未知版本不能静默按 v1 解释 |
| `target.board/revision/mcu_ref` | 非空字符串，来自项目资料或用户确认；更新不得换对象 |
| `source_binding.hash_policy` | 固定为 `sha256-text-lf-binary-raw-v1` |
| `inputs` | 非空列表，包含全部实际用于提取事实的输入；不允许重复路径 |
| `inputs[].path` | 相对项目根目录、使用 `/` 的文件路径；非 URL、绝对路径、盘符路径或上级目录穿越；解析后的文件仍在项目内 |
| `inputs[].hash_mode` | `text-lf` 或 `raw`；capture 按当时的文件内容及 Git LFS 属性选择，后续检查固定使用此模式 |
| `inputs[].sha256` | 由工具生成的完整摘要；不是 Git commit SHA，也不截短 |

所有 source 文件必须能读取实际内容。来源集合只覆盖明确声明的文件，未声明依赖无法靠 SHA 自动发现。目标标签正确与否、提取内容是否准确仍需按来源核对。

## 2. 摘要规则与边界

capture 复用现有 `artifact-conventions/scripts/registry_check.py` 的内容约定选择模式，不新增语义归一化：

- Git LFS 跟踪的已展开文件，以及含 NUL 字节的文件，记录 `hash_mode: raw`，按原始字节计算 SHA-256。
- 其余文件记录 `hash_mode: text-lf`，将 CRLF、CR 转为 LF 后计算；不改编码、空格、注释、排序或导出时间戳。
- **区别于登记表工具**：未展开的 LFS 指针不能作为可用来源，不能只取其 oid 就声称已读取。capture/check 都明确报告内容不可用。
- capture 在 Git 工作树中需要能查询 Git 属性；Git 缺失或属性查询失败时明确报告无法核验，不默认为“非 LFS”。无 Git 元数据及属性的普通目录可使用内容规则。
- check/publish 按每个输入已记录的模式计算，不依赖本机是否安装 Git，也不因当前 `.gitattributes` 改变而悄悄换算法。重新生成才重新选择模式。

输入包含文字但按 LFS 存储时仍按 raw 计算；UTF-16 文件含 NUL，同样按 raw 计算。不得把该策略等同于所有文件逐字节相同，也不得宣称忽略换行以外的内容变化。

`CURRENT` 只表明检查当时所有声明输入按该策略匹配，之后文件仍可能变化。不在产物中保存“永远有效”状态，不因全仓库 HEAD 改变或无关文件修改而判过期。

## 3. 快照、正文和完整写入

用户操作为 create/update/check；内部辅助命令为 capture/publish/check。

1. `capture` 读取明确列出的源文件，把原始字节复制到指定新目录的 `sources/<仓库相对路径>`，并生成 `manifest.json`。manifest 保存公开元数据和用于检测副本变动的内部信息。
2. Agent 根据 `sources/` 中的副本生成临时正文。副本未经修改；需要其他来源时重新捕获完整集合，不在生成中混入新版本活动文件。
3. `publish` 检查快照和当前源文件，组合元数据与完整正文，一次性写入目标 Markdown。检查失败不覆盖旧产物。`--replace` 只用于更新，同一目标路径不能改为别的板卡版本或 MCU；更新保留原权限，新文件按普通文件创建权限及进程 umask 创建。
4. 完成后 `check` 只读复核来源。脚本不会判定正文的连接关系是否正确；Agent 必须按源文件回查，不得把 publish 成功当成提取准确性测试。

快照是临时工作文件，不是新登记表，也不是防篡改的签名证明。更新必须重新提取；脚本不提供只改来源摘要的命令。完整重读后正文没变是正常情况。

人工备注由下面的唯一标记区界定；更新时保留旧区块。不要在自动提取表格里保存手工修正；需要修正事实，应先修正或补充实际来源再更新。

```markdown
<!-- manual-notes:start -->
人工备注正文
<!-- manual-notes:end -->
```

## 4. 检查状态

| 状态 | 退出码 | 含义 |
| --- | --- | --- |
| `CURRENT` | 0 | 所有声明来源存在、可读且摘要匹配 |
| `STALE` | 1 | 至少一个可读取来源的摘要变化 |
| `UNVERIFIABLE` | 2 | 输入/元数据无法完整校验，例如文件缺失、格式错误或只有 LFS 指针 |

逐文件输出期望和实际摘要；无法计算时报告原因。混合问题中有任何无法核验项时，总结果为 UNVERIFIABLE，已发现的变更仍需列出。

来源变化时，只停止依赖这份派生资料作新的确定结论。可重新生成，或直接读取源文件继续；不强制全仓库重建、不增加审批、不阻止无关工作。

## 5. 内容证据与消费规则

- 物理脚位、GPIO 名、网络名和对端脚位是不同字段，不能互相代替。源文件没有某字段就写待确认。
- 同网直连与经电阻/跳线/转换器的信号路径分开。网名里的 SPI 实例、复位极性、ADC 提示不替代手册证据。
- 每条连接用源文件相对路径和器件/脚位/网络定位，行号可辅助但不替代这些标识。
- 可在来源说明定义 `S1 = <相对路径>`，表内用 S1 及网络/端点定位。避免逐行重复长路径和相同的未知项说明；此资料用于按需速查，不复制完整网表或通用审查清单。
- 网表没有某引脚不等于该引脚 NC；说明导出覆盖范围。目标 MCU 的未解释脚和参数集中列出。
- 数据手册确实用于判定复用、电压、时序等时，把其文件加入 inputs；只有手册链接但没读到内容时不把参数当确定事实。
- 原理图 SHA 与网表 SHA 同时存在也不证明导出关系。本版只绑定实际读取的文件，不自动建立上游生成链。
- 资料结论为 L0，不能证明实板状态。飞线、装配差异等在独立备注或证据记录中说明对象和来源。

消费者确认 target 后运行 check，匹配才按需读取相关章节；未知项继续查证。元数据不会让普通 Agent 自动遵守规则，需通过项目现有规则或消费者工作流接入。

## 6. 与现有管理方式配合

项目画像只链接此文档，由 project-profile 维护；本 skill 不写画像。纳管依据项目已有的文件类型声明，不因文件扩展名或来源绑定而强制纳管。

登记表的 `sha256` 检查**产物自身**，本文的 inputs 摘要检查**产物依赖的来源**。更新登记表中某个文件的摘要不代表其他派生资料已经重新生成，也不能替换这些资料的 inputs 摘要。源文件未变但正文被改，来源检查可能仍然 CURRENT；需要产物完整性检查时复用现有登记表功能。
