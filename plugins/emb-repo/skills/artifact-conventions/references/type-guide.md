# 受管理工程文件类型 · 默认目录与扩展原则

**从工程职责识别，不从文件后缀、目录名、篇幅或重要程度识别。** 正式用途可能由项目声明，因而一份很短的规范也可能受管理，长篇个人调试笔记也可能不纳管。

| 推荐类型 | 归属的内容 | 何时有必要纳管 |
| --- | --- | --- |
| `requirement` | 产品/系统需求、验收目标和关键约束 | 被团队作为需求基线或追溯目标使用 |
| `reference` | 厂商数据手册、硬件原理图、行业标准、法规等原始依据 | 被工程决策或实现引用为版本化外部约束，且原件已放入仓库 |
| `design` | 系统架构、板卡职责划分、实现路线或正式设计方案 | 方案需被多人/模块共享、复用或长期演进 |
| `decision` | 重要架构取舍的 ADR | 符合 `emb-design:adr-write` 的取舍与人类确认门槛 |
| `specification` | 协议、接口行为、错误处理、兼容规则等可验证契约 | 多个实现者/消费者需要共同遵守 |
| `verification` | 验证计划、判据、验收报告或可复核测试记录 | 作为测试状态或合规依据正式引用 |

这六种是**起点而非完整清单**。项目可以增加：
- `risk-analysis`：正式风险评估；
- `production-spec`：生产制造或测试工艺；
- `calibration-record`：校准数据与校验条件；
- `safety-case`：产品安全论证；
- 其他项目需要管理的工程资产。

这些扩展只是示例，并非本 Skill 强制所有项目采用。新类型在登记表的 `types` 中声明名称和 `purpose`，如有必要规定自身的批准过程和修订策略；复用共同 `id/type/path/status/scope` 形式。

## 不纳管的典型对象

普通源码、构建配置、工具脚本、开发日记、临时抓包、简单 README、尚在随手推演的草图、AI 临时计划等，**不会仅因属于工程仓库而纳入登记**。它们仍服从版本控制、安全、编码、项目目录等通常约定。

**只存在于仓库外的内容**（飞书文档、网盘文件、在线表格、厂商网页等）也不登记：它们不在本仓库的管理范围内，无论多重要。需要纳管时，先由负责人把文件或其导出快照提交进仓库，再按类型登记；原链接可写入条目的 `source` 字段。

对边界情况，看**是否已获得上述正式职责**，而不看标题。比如：
- 一份 `notes.md` 被各个板卡依赖、正式定义 I2C 错误恢复行为：可能实质上是 `specification`，不应因文件名叫“笔记”而忽略。
- 一份 `display-idea.md` 只比较实验路线：当前可能仍是自由探索；被采纳为共享方案后，再登记其正式 Design 版本。
- ADR 可以是 Proposed 并已登记，但 **Proposed 不是 Accepted**。
- 外部 PDF 无法在文件内部写元数据：放入仓库后直接索引二进制文件并登记准确版本、路径及适用范围；不改 PDF 正文。项目启用完整性校验后，条目上的 `sha256` 同时记录了“用的是哪一份文件”。

## 类型误判时的最小动作

若项目未声明相应类型、没有证据说明其是否属于共同基线，则标为“待确认是否纳管”，询问用户文件的预期用途。不要以自创文件类型覆盖现有分类；也不要把所有文件默认视为“最好全部纳管”。

当已有受管理类型文件遗漏在表外，说明“登记不一致”，并建议补录；是否处于 Approved/Accepted 状态需要项目真正的批准依据。
