# 工程文件登记表规范 · Registry Conventions

## 1. 定位

每个项目至少设置一个明确的工程文件登记入口，推荐 `docs/engineering-artifacts.yaml`（项目已有正式路径时不要再建一个）。此登记表**显式声明当前纳入管理的文件**；不是完整仓库文件清单，也不是专业文档内容的镜像。

**登记范围以仓库为边界**：只有已提交到本仓库的文件才能登记、受管理。飞书、网盘、在线表格、厂商网站等外部系统中的内容不在本仓库的管理范围内；需要纳管时，由负责人把文件或其导出快照提交进仓库后再登记。外部链接只作为来源说明，可写在条目的 `source` 字段或文件正文中，不单独成为条目。这样，受管理文件的内容、修订和（启用时的）hash 都能随仓库版本控制，任何人检出同一提交看到的都是同一份依据。

YAML 用于可读、可 diff、可由程序解析。文件一旦登记，说明它是工程管理对象，**不说明已经批准或验证**。登记表及相关内容随项目版本控制，受管理类型可逐步增加。

[最小示例](../assets/engineering-artifacts.example.yaml) 仅供复制/扩展，不是特定项目的事实。

## 2. 统一的形式

建议登记表根字段：

| 键 | 用途 | 规则 |
| --- | --- | --- |
| `schema_version` | 登记表结构版本 | 从 `1` 开始；改变不兼容格式时再升级 |
| `types` | 项目声明的受管理类型 | 以类型名为键，定义识别用途（`purpose`）；可新增项目专有类型 |
| `artifacts` | 当前受管理文件清单 | 数组；每项至少有下述五个字段 |

每项登记条目的最低信息：

| 字段 | 含义 | 约定 |
| --- | --- | --- |
| `id` | 稳定身份 | 在一个项目中唯一；重命名/移动文件不得自动更换 ID |
| `type` | 文件类型 | 必须在 `types` 中声明；不是依据扩展名判断 |
| `path` | 唯一定位 | 仓库根相对路径，指向仓库中的文件；不要放机器本地绝对路径或外部链接（URL） |
| `status` | 通用生命周期 | 初始可为 `draft`；从专业批准依据确认其是否可作为当前工程依据 |
| `scope` | 适用范围 | 显式说明产品、板卡、版本或项目全局范围；不允许空白 |

推荐状态名称（项目可以定义更细映射）：

- `draft`：正在起草或审议，**不是被批准的约束**。
- `active`：在**声明的适用范围**内作为当前工程依据（不是声明实现已完成、验证已通过）。
- `superseded`：已被明确的后继依据取代，历史保留供追溯。
- `archived`：不再当前使用、保留记录；不可直接视为生效依据。

`scope` 推荐使用非空字符串列表，以 `["project"]` 表示全项目，或 `["product:alpha", "board:rev-b"]` 表示限定范围。范围待核实时显式标注 `["pending"]`，**不能把 pending 当成无限适用**；状态推进到 `active` 前需要确认范围。项目可自定义可机器识别的维度词表，不要求所有项目同一套板卡标识。

可选字段：`revision`（按类型要求，不强制统一 SemVer）、`supersedes`、`source`（来源说明，如外部原件的下载地址或导出自哪份在线文档）、`owner`、`verified_by` 等；仅当实际有依据时记录。不要编造不存在的依赖关系或验收记录。项目启用完整性校验后，每个条目还有由工具写入的 `sha256`，见第 6 节。

## 3. 登记表与文档内信息的权威分层

- **登记表权威**：`id/type/path/scope` 与**通用生命周期**，回答“管理了什么、在哪里、当前是否作为有效入口使用”。
- **文件或专业系统权威**：文档的规范性条款、技术设计、具体修订、ADR Proposed/Accepted 等类型专属批准状态、测试原始记录和通过/失败结论。
- `status: active` 不代替 ADR Accepted、需求签署或协议批准。若存在类型专属状态，需有一致的映射；例如 ADR Proposed→draft，Accepted→active，Superseded→superseded（只是**示例映射**，以项目实际 ADR 流程为准）。
- 两边信息冲突时先核实事实、审批记录和适用版本，报告冲突。**不要把登记表字段视为可以直接覆盖专业状态的指令，也不要悄悄重写登记表来贴合未经确认的正文。**

不可编辑的外部资料（数据手册、标准等）把原件放入仓库后，也可直接出现在 `artifacts` 中：`path` 指向仓库中的原件，`revision` 使用来源的厂商/法规修订号；复杂来源证明及校验值留在伴随文件或类型专有字段，不改原件内容。

## 4. 类型与索引的演进

- 创建项目登记表时先确认项目既有的文档约定，不重复创建第二个根入口。
- `types` 可由项目根据真实需要扩展。每新增类型应说明它负责什么、什么样的文件触发纳管，与既有类型如何区分，必要时定义修订和状态语义；**不需要先修改通用 Skill**。
- 创建属于已声明类型的文件时，默认在同一逻辑变更中登记；没有登记视作待修正的管理不一致。Draft 一开始就能登记。
- 旧项目第一次采用登记表时，允许标记迁移进度（例如可选 `coverage: partial`），渐进补录受管理文件。声明“已全部登记”前需实际核查，不能用空索引掩盖遗漏。
- 文件改名、移动或被取代时更新原记录并保留 ID/适当取代关系；删除、废弃不得暗中丢掉关键历史追溯。
- 如果 `types` 已扩展到风险、安全、生产、校准等类型，普通源文件和临时脚本**仍不自动变为管理对象**。

## 5. 常见一致性检查（建议而非强制门禁）

1. 同一个 `id` 是否重复？是否有多个根索引互相争权？
2. `type` 是否在 `types` 声明？`path` 是否存在或正作为本次变更新建？
3. `scope` 是否非空且适用对象可理解？`status` 能否找到类型专属批准依据？
4. 与项目已有 ADR、协议、验证报告的状态是否相容？是否把“草案/Host 通过”误当正式批准/实板验收？
5. 受管理类型的新文件是否漏登？是否误把普通文件加入管理？

不在通用 Skill 中规定强制审批、CI Gate、完整迁移期限或特定项目的命名规则；需要更强约束时由项目按其实际管理能力自行采用。

## 6. 完整性校验（可选，由项目启用）

项目希望在 CI 中**形式化地发现受控文件被修改**时，在登记表顶层声明：

```yaml
schema_version: 1
integrity: sha256          # 启用后，每个条目都必须有 sha256
artifacts:
  - id: SPEC-LINK-001
    type: specification
    path: docs/protocols/link-v1.md
    status: active
    scope: ["project"]
    sha256: 3f9a…c21e      # 由 registry_check.py update 写入，不手填
```

未声明 `integrity` 的项目不受影响，仍按前几节轻量登记。

启用后对登记表的两点格式要求：

- **编码为 UTF-8**（与仓库中其他文本一致）。工具总是按 UTF-8 读取，不受 Windows 中文系统的本地编码（cp936 / GBK）影响。换行符用 CRLF 或 LF 都可以，`update` 会保留文件原有的换行符。
- **条目用块状写法**，每个字段一行（如上例）。单行的 flow 写法 `- {id: …, path: …}` 能被正确读取和检查，但 `update` 无法安全地改写它，会报错并保持登记表不变，需先改为块状写法。

### 6.1 hash 怎么算

由 `scripts/registry_check.py` 计算，规则固定，保证不同机器结果一致：

| 文件 | 计算方式 | 原因 |
| --- | --- | --- |
| Git LFS 指针文件 | 直接取指针里的 `oid sha256:` | CI 检出时通常没有 LFS 内容；该 oid 本来就是原文件的 sha256 |
| LFS 跟踪的文件、含 NUL 字节的二进制文件（PDF、图片等） | 原始字节的 sha256 | 与 LFS oid 一致，不改变二进制内容 |
| 其他文本文件 | 先把 CRLF / CR 统一为 LF，再算 sha256 | Windows（`autocrlf`）与 Linux 检出结果一致 |

### 6.2 CI 检查什么

`registry_check.py check --base <目标分支>`：

| 检查 | 失败时 |
| --- | --- |
| 每个条目的 `path` 存在、`type` 已声明、`scope` 非空、`id` 不重复 | 登记表本身有误 |
| 文件内容与 `sha256` 一致 | 受控文件被修改，但没有在登记表中留痕 |
| 状态为 `superseded` / `archived` 的条目（以基线为准），`sha256` 未被改动、内容未变 | 冻结文件被修改；应新建修订并用 `supersedes` 取代 |
| 基线中已冻结的条目，在当前登记表中仍然存在 | 冻结条目被删除；冻结条目须保留以供追溯 |
| `--base` 指向的引用可以读取 | 基线无效（未 fetch、拼写错误）时以退出码 2 报错，**不会**静默跳过冻结检查；基线有效但其中还没有登记表（首次启用）时提示后继续 |

按状态的要求：

| 状态 | 文件内容变化时的要求 |
| --- | --- |
| `draft`、`active` | 在同一变更中运行 `registry_check.py update <id>` 更新 `sha256` |
| `superseded`、`archived` | 冻结，不允许修改；已有 hash 时 `update` 默认拒绝改写（首次写入基线不受限），只有确需修正（如修复错误归档）时才加 `--allow-frozen`，并在 PR 中说明 |

### 6.3 hash 不等于审批

hash 变化只说明“受控文件变了”，**不说明改得对、也不说明已经批准**：任何人都能运行 `update`。它的作用是让每一次受控文件的改动都在 PR 的登记表 diff 中显式出现，便于评审。需要强制由特定的人把关时，再配合仓库的评审规则，例如为登记表设置 CODEOWNERS（模板见 `assets/ci/CODEOWNERS.example`）。类型专属的批准（ADR Accepted、协议批准）仍按第 3 节由专业流程负责。
