# 工程知识、文档角色与 ADR 判断

## 1. 外部依据 → 系统方案 → 当前契约 → 实现与验收

这是一条有反向反馈的**工程依据主线**，不是要求每项工作必须走完的审批流水线：

| 对象 | 主要回答 | 位置与管理 |
| --- | --- | --- |
| 外部事实/约束 | 实际器件、法规、原理图和物理限制是什么？ | 有来源、修订、料号/板卡适用性；原件保留 |
| 内部需求 | 为什么需要该能力，验收什么？ | 需求系统/项目需求文件，批准版次 |
| 系统方案 | 为什么如此划分设备/模块职责？ | 版本化设计，明确适用场景与假设 |
| 协议/工程契约 | 消费者之间必须保证哪些外部行为？ | 稳定标识、版本、批准状态、接口/失败语义 |
| 实现方案 | 在不破坏契约前提下如何组织技术实现？ | 允许演进、重构和替换 |
| Issue | 当前发现了什么现象/问题、试验和未解决事项？ | 记录当前可复现情境、证据和下一步 |
| ADR | 为什么选择这个重要的非显然取舍？ | 背景、否决方案、代价与替代/取代关系 |
| 代码与构建 | 哪些源文件和配置构成某个交付目标？ | Git、构建系统中的真实依赖与版本 |
| 验证计划/证据 | 如何验证符合要求？实际证明了什么？ | 判据与结果分离，绑定硬件、固件、条件 |

工程演进可以跨多轮：证据反馈到需求和方案，协议不变时可更换实现，多种实验代码可以并存而不必进入产品主线。

## 2. ADR 的准入门槛

问两件事：

1. **未来的维护者如果只看当前协议和代码，是否仍会问“为什么不是另一种同样合理的架构”？**
2. **如果其他人或 AI 擅自推翻，会不会改变跨板、跨模块、出厂兼容性或既有交付计划的共同前提？**

符合其中重要取舍、并且理由需要长期解释时，考虑 ADR。尤其是：板卡关键选型、Bootloader 持久记录兼容、跨设备协议路线、不可逆硬件与维护能力边界、关键资源所有权。

不为参数调整、短期探索、普通模块抽取、已由协议直接决定的字段、可反复推翻的工作假设制造 ADR。临时探索先留在 Issue/PR；确定其他工作可以依赖的版本化工程契约后，只有**值得长期解释的取舍**需要 ADR。

- ADR **不替代**协议（精确规范）或方案（当前实现路径）。
- 一项选择可以是**阶段性承诺**，并非永久真理。
- 草案与正式通过的状态不同； `Accepted` 和 `Superseded` 均须符合项目的审批与追溯流程。
- 修改过去 Accepted 的取舍，不覆盖历史背景；按照项目规则起草取代/修订记录，取得授权后生效。

## 3. 追溯而不制造文档爆炸

普通源码通过所属 Component/Board/Program 间接追溯到契约；不能要求每个函数都手工附同一文档链接。涉及线格式、安全、持久化兼容、共享硬件资源等关键行为可以精确关联条款 ID。

实现关系从构建系统（如 CMake）读取，而不是维护第二份易过期的源码列表。每个 Target 的 MCU、硬件版本、宏/配置变体要能区分。验证条款应该能指向真实测试与实测记录，未测不能当已通过。

同一个数或同一条规则只在一处权威。跨模块的合计、优先级和取舍放在联合文档，模块文档只写自己，见 [document-boundaries.md](document-boundaries.md)。

优先保存少数**当前有效**、版本明确的入口；历史方案和原始实验用于回答“当时为什么、测到什么”，不应让后来者依赖它们理解今天的系统。
