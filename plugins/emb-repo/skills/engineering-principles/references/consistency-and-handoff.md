# 冲突、证据、演进与交接

## 1. 探索冲突 vs 主线冲突

- 开发分支/实验可以持有不同假设或替代方案，只要隔离其作用范围，不能误导其他工作认为已经正式批准。
- 发现交叉问题时，先核对双方依据的**版本、批准状态、目标产品和测试条件**。看似冲突的结果可能是在不同适用域下同时正确。
- 准备合入共同主线前，必须明确解决现有行为契约的相互矛盾：统一方案，或正式批准多版本共存及兼容规则，并对各受支持配置验证。
- “留一条注释说明这里例外”“先合并以后再说”不是消除冲突。记录已知缺陷是允许的，但不能将不满足的正式验收条件谎称已通过。
- 若会改变产品风险取舍、外部协议、不可逆硬件决策，应由有授权的人确认；此 Skill 只指导如何识别，不执行门禁。

## 2. 三种不同状态

| 维度 | 常见状态 | 不能推断 |
| --- | --- | --- |
| 规范/方案 | Draft / Proposed / Accepted / Superseded | 存在于主分支就一定批准 |
| 代码 | Not Started / Partial / Implemented | 代码实现就代表满足规格 |
| 验证 | Not Run / Passed / Failed / Blocked | 通过 Host Test 就等于真实硬件可用 |

证据应能回答：哪个板卡/批次、哪个固件 SHA/构建参数、哪个仪器/工况、测试期限和原始结果。若项目使用 L0–L4，资料计算、模型/主机、台架、整机、第三方认证各自只证明该等级的结论。

## 3. 演进中的最小反应

- **局部实现调整**：保持当前契约，验证相应组件及消费者。
- **契约变更**：列出消费者、兼容范围、待作废的测试结论及当前可用版本，先提出变更供相关负责人确认。
- **外部事实变更**：回到相关器件/原理图/法规来源，区分新证据与旧假设，必要时重新审视方案和 ADR。
- **多人/Agent 工作**：每个任务明确已知目标、适用版本、不可改边界和验收证据；发现需要越界时提出问题而不是偷偷扩大任务范围。

优先级只作为多维判断：产品时效、阻塞影响、风险与可验证程度都会影响当前顺序；本 Skill 不决定项目排期。

## 4. 有界诊断与可交接性

当出现故障，新接手者应从当前 Issue / 模块文档直接获得：
- 当前适用的硬件、固件、配置和协议；
- 真实现象、复现条件、可复核证据与不确定项；
- 负责模块、相关接口和可进行的下一项有效实验。

历史讨论可以支持追溯，不能代替当前明确的接口与测试。工程可以复杂，但恢复**可行动的诊断上下文**不应要求阅读十几个历史 PR。不要虚假承诺所有间歇性故障都能在固定时间内找到根因；缺少证据时指出最值得补测的变量。
