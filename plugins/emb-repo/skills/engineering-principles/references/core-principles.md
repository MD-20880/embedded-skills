# 默认工程原则 · 轻量版

当 `emb-repo` 插件启用时，以下原则适用于日常工程工作；它们是**判断默认值**，不是要求每个任务写管理报告。项目已有的正式约束和用户明确要求优先；确需例外时说明原因和适用范围。

1. **角色分明**：需求说明需要什么，外部资料提供约束；方案说明怎么选，协议/契约规定必须保证的行为；Issue 记录问题与探索，ADR 解释重大取舍；代码是实现，测试与实测是证据。
2. **区分假设与承诺**：实验假设可以反复推翻；只有明确范围和版本的工程承诺，才适合作为其他工作稳定依据。
3. **依当前有效依据工作**：优先确认版本、审批状态、板卡/固件配置及当前契约；历史和 Demo 供追溯，不能自动作为今天的规范。
4. **冲突不能静默进入主线**：开发可隔离探索；合入共同基线前要消除互相矛盾的契约。若正式支持多版本，应有清楚的适用范围、兼容规则与验证，不是用 TODO 掩盖冲突。
5. **事实、实现、验证分离**：规范写完不代表代码实现；Host Test、静态检查不等于实板验收。关键结论绑定来源、对象、版本和证据，未知就说明未知。
6. **有界可理解与可诊断**：交付应从少量当前有效入口找到负责模块、影响范围、验证与下一项有效实验；关键知识沉淀到它应归属的文件，不能要求后来者阅读全部聊天和历史 PR。

优先级会随产品阶段、依赖阻塞和风险变化，但具体调度由项目工具和专业 Skill 承担。**普通任务保持轻量**：不添加没有价值的流程和文档；遇到跨边界变更再查阅 `/emb-repo:engineering-principles` 或相应专业 Skill。
