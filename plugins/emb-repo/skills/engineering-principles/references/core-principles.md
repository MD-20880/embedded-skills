# 默认工程原则 · 轻量版

`emb-repo` 插件启用时，以下原则作为日常工程工作的**判断默认值**，不要求每个任务都写管理报告。项目已有的正式约束和用户的明确要求优先；确需例外时，说明原因和适用范围。

1. **角色分明**：需求说明要什么，外部资料（手册、原理图、法规）给出约束；方案说明怎么选，协议 / 接口契约规定必须保证的行为；Issue 记录问题和探索，ADR 解释重大取舍；代码是实现，测试和实测是证据。
2. **区分假设与承诺**：实验中的假设可以反复推翻；只有写明范围和版本的工程承诺，才能作为其他工作的稳定前提。
3. **依当前有效依据工作**：先确认版本、批准状态、适用的板卡和固件配置，以及当前生效的契约；历史记录和 Demo 用于追溯，不自动等于今天的规范。
4. **冲突不能静默进入主线**：开发中可以隔离探索不同方案；合入共同主线前，必须消除相互矛盾的契约。确需多版本并存时，写清适用范围、兼容规则并逐一验证，不能用 TODO 掩盖冲突。
5. **事实、实现、验证分离**：规范写完不等于代码实现，代码实现不等于验证通过；主机测试和静态检查不等于实板验收。关键结论要绑定来源、对象、版本和证据，不知道就写明不知道。
6. **交付可接手、问题可诊断**：交付物要让人从少数几个当前入口找到负责模块、影响范围、验证方法和下一步可做的实验；关键知识写进它应归属的文件，不能要求后来者翻遍聊天记录和历史 PR。
7. **受管理文件有入口**：创建工程文件时先判断其是否属于项目声明的受管理类型；是则按 `/emb-repo:artifact-conventions` 在 YAML 工程文件登记表中声明身份、状态与适用范围；不是则不额外登记。登记不是批准。

优先级会随产品阶段、阻塞情况和风险变化，具体排期由项目工具和专业 Skill 负责。**普通任务保持轻量**：不添加没有价值的流程和文档。遇到以下情况，先调用 `/emb-repo:engineering-principles` 加载完整判断方法，再回答：契约或协议版本冲突、多版本并存、草案与正式规范混淆、跨模块或跨团队的变更、多人或多 Agent 并行开发的边界、交付与交接。具体的 ADR、Issue 操作交给相应的专业 Skill。
