# 文档边界：每份文档只写自己

一个设计里的内容放在哪份文档，决定了以后改一处要不要改五处。本文给出两条边界规则：模块文档只写本模块的业务，跨模块的取舍上移到联合文档；`docs/` 以外的 README 在本目录内自包含。

## 1. 模块文档只写自己

单独拆出来的模块单独设计，第一要务是把自己的业务做完。模块文档只写五件事：

1. 要完成什么：目的和范围。
2. 内部状态和流程。
3. 对外提供的接口。
4. 依赖的接口：只写“我需要对方提供什么”，不写对方怎么做到。
5. 自己的资源需求和自己的验证。

### 1.1 判别：留在模块，还是上移

模块可以写“我需要什么、我占多少”。例如“取块间隔必须小于 15 ms”“上行占 34.6 kB/s”“每个总线事务最长 4 ms”。

下面这些上移到联合文档，模块文档里只留一行引用：

| 内容 | 例子 |
| --- | --- |
| 和别人加起来够不够 | 带宽合计、CPU 合计、RAM 合计、余量 |
| 谁让谁、谁先谁后 | 优先级、抢占、调度顺序、共享总线或请求窗口的份额 |
| 因为别人而定的参数 | “因为显示整帧 8.3 ms，所以缓冲取 4 块” |
| 别人出问题时我怎么联动 | 另一块板升级期间其他服务怎样、断链时各业务怎样 |
| 多个模块同时运行的验证 | 并发、耦合、混合业务的验收场景 |

判断方法：把这段话里的其他模块删掉，如果它还成立，就留在模块里；如果它只在“和别人放在一起”时才有意义，就上移。

### 1.2 联合文档

联合文档负责“大家放在一起”：收集各模块写下的需求和占用，在一处算合计、定优先级、给出取舍。按共享的资源或运行环境划分，例如“某块板的联合运行”“某条板间链路的联合预算与调度”，不按功能划分，也不合成一份什么都写的总文档。业务之间的仲裁（画面、资源优先级、系统条件）如果已有应用或交互规范承担，就由它承担，不另起一份。

### 1.3 引用方向

```text
产品层   需求、交互稿、术语
  │
系统层   联合文档：合计、优先级、取舍、联合验证
  │
模块层   各模块设计：只写自己
  │
接口层   线格式、接口契约
```

- 模块文档只引用接口层和自己的需求。
- 联合文档引用模块文档里的“我需要、我占多少”，不在模块里重算。
- 模块之间不互相引用参数。一个模块的设计被另一个模块的参数牵着走，说明这个参数应该在联合文档里定。
- 同一个数只有一处权威。几份文档各写一遍同一个合计，迟早会互相矛盾。

### 1.4 迁移已有文档

已有文档混写时，按下面的顺序拆，任何时候仓库里都只有一份权威数值：

1. 先只新增联合文档：从各模块搬来内容，重算合计；登记为受管理文件（如项目启用了登记表）。
2. 再删模块里的复述，改成一行引用；每份升小版本，写版本记录。
3. 合并数值时发现矛盾，列出各处的值，按最新实测或最新文档取，交给负责人确认，不静默选一个。

## 2. README 在本目录内自包含

`docs/` 以外的 README 说明它所在的目录，读者应能只看这个目录就理解它。

- 只写本目录的内容。其他目录的设计写在它们自己的 README 里。
- 用到的事实、数值和规则连同来源抄进来，不写“见 X”“同 Y”。
- 不使用别处定义的编号（例如外部清单里的 H1–H17）。
- 可以链接外部文件，但理解本文不能依赖它们。外部文件列在“参考（外部，非依赖）”一节。
- 源文件头注释指向本目录的 README，不指向别的目录。

`docs/` 下的文档本来就是互相引用的规范体系，不受这条约束，但仍遵守第 1 节的引用方向。
