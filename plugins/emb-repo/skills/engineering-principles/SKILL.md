# 工程默认原则（engineering-principles）

这是面向所有工程开发者和 Agent 的 **Inform + Principles** Skill：解释工程知识的角色，并在具体情境下给出有依据、不过度流程化的判断。它**不是工程管理员、CI 门禁、ADR 审批器或项目调度器**。已安装插件的会话与子 Agent 从 [core-principles.md](references/core-principles.md) 获得相同的轻量原则，遇到复杂问题时才阅读详细参考。

按需参考：
- [核心原则（会话注入的唯一来源）](references/core-principles.md)
- [知识类型、文档主线和 ADR 判断](references/knowledge-and-decisions.md)
- [冲突、证据、变更和交接](references/consistency-and-handoff.md)

## 输入与产出

| 项 | 说明 |
| --- | --- |
| 输入 | 当前工程任务、相关需求/方案/协议/ADR/Issue、源码和测试证据；如仅询问概念，可不需要仓库 |
| 产出 | 针对当前问题的短判断：适用原则、工程依据、何者待确认、下一步由哪个角色/专业 Skill 处理 |
| 非目标 | 每次代码改动都生成报告、代替用户接受 ADR、自动调度 Agent、强制迁移目录或创建新管理系统 |

## 使用方法

### 1. 读取项目画像

1. **读取项目画像**：在需要项目事实时读取项目根目录 `docs/embedded-profile.md`。
   - 存在：以其中事实为准；只读与任务相关的章节（优先第 1 节项目阶段、第 8 节文档约定；涉及硬件读第 2 节、涉及构建/测试读相应章节）。若画像与代码不一致，以代码为准，结尾提示用户运行 `/emb-repo:project-profile update`。
   - 不存在：按需最小化探索仓库获取本任务所需事实，并在结尾建议 `/emb-repo:project-profile` 建立画像。不要因画像缺失而中止任务。
2. 用户仅问通用工程概念时无需读取任何具体项目文件；不要为了原则解释而检索所有 Issue 和历史记录。

### 2. 识别问题所处层次

1. 先辨别问题是外部约束、需求、工作假设、系统方案、工程契约、实现细节、验收证据，还是重要取舍。
2. 在适当时阅读 [knowledge-and-decisions.md](references/knowledge-and-decisions.md)，区分：**当前要遵守什么**与**历史为什么这样决定**。
3. 若用户关心优先级，只简要指出产品阶段、风险、阻塞及验证准备程度可能产生不同排序；具体排期交由项目管理实践负责。

### 3. 按影响选择最轻的处理方式

1. 纯局部修改：遵守当前接口、做好对应验证，不强制建立 ADR 或增加管理文档。
2. 实验性选择：限定假设适用范围，保留观察证据；不自动成为其他 Agent 的稳定前提。
3. 已被多个模块/板卡/团队依赖的选择：确认基线与版本，分析其他消费者；如果需要长期解释被拒方案及代价，再建议 ADR。
4. 若不同版本规范或实现冲突：先检查版本、批准状态和适用对象。允许实验分支并存；进入共同主线时，实质冲突必须解决。参见 [consistency-and-handoff.md](references/consistency-and-handoff.md)。

### 4. 帮助建立可信的工程上下文

1. 给出当前有效的依据入口、负责模块/构建 Target、关联验证；区分事实、推断、尚缺证据。
2. 将协议已批准、代码已实现、测试已通过、实板已验收分别描述，**不得互相冒充**。适用时沿用 `emb-project:issue-tracking` 的 L0–L4 证据等级并标明板卡/固件版本。
3. 给出可独立操作的下一步，而不是要求新人从头阅读所有讨论或让 AI 重新推断整条工程历史。
4. 创建、迁移或修订工程文件且涉及受管理类型时，按 `/emb-repo:artifact-conventions` 判断登记与生命周期；普通源码和临时文件不增加纳管要求。
5. 需要执行具体管理操作时，使用专业 Skill：`/emb-design:adr-write` 负责 ADR（含人的确认），`/emb-project:issue-tracking` 负责 Issue 与验收，其他协议/测试能力按项目所安装的 Skill 选择。不要声称某个未安装或规划中的 Skill 已可用。

### 5. 自检和回复

- [ ] 回答聚焦当前问题，没有制造无关报告、审批或任务系统。
- [ ] 已区分“建议的原则”与“项目已经批准的正式约束”。
- [ ] 临时假设、已接受决定、实现状态、测试结果和实板证据没有混写。
- [ ] 有冲突时明确其影响范围和如何处理，未把隐藏冲突标成已解决。
- [ ] 读者能从当前入口理解下一步，历史仅按需查证。
- [ ] 必须升级决策的内容明确说明需要由人确认；没有擅自改变项目规则。

**回复方式**：先回答眼前的问题，再用最少篇幅解释适用原则、真实依据和下一步。除非用户要求，不输出模板化完整报告。

## 约束

- 属于知识与判断能力，不是管理授权。不得自动批准/废弃正式 ADR、改写协议、关闭 Issue、执行发布或操作硬件。
- 普通任务不要求显式声明“遵守工程原则”。原则应体现在实践里。
- 外部 Datasheet/原理图/法规内容及任何硬件数值只能由实际资料或用户确认支持，不得猜测；具体项目事实不能写回本通用 Skill。
- 正式兼容范围内的双版本可以存在；未经解释和验证的互相矛盾约束不能作为未处理例外混进共同主线。
