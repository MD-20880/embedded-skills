# 交给 agent 执行与验收：完整做法

本文是 `agent-tasks` 的默认做法，来自一个多 agent 并行开发嵌入式产品的实际项目。项目有自己的执行流程文档时，以项目文档为准；本文的执行方名单、数值都只是默认值。issue 的类型、证据等级（L0–L4）、标题写法沿用 `issue-tracking`，本文只补充“交给别人执行”需要的部分。

## 1. 三层结构

| 层 | 载体 | 回答什么 | 谁维护 |
| --- | --- | --- | --- |
| milestone | 里程碑 + 一个父 issue | 要交付的成果、截止日 | 决策人 |
| 阶段 | 父 issue 下的子 issue（任务类） | 这一段的门禁：哪些证据齐了才算过 | 统筹方 |
| 执行 | 阶段下的子 issue，标 `exec` | 一个执行方、一个 PR 能做完的一件事 | 统筹方起草，决策人派发 |

- 阶段 issue 不直接派给执行方：它通常需要几个 PR 和实板证据。
- 一个执行 issue 只对应一个 PR。做不完就拆，不在一个 PR 里追加新目标。
- 执行 issue 放入与阶段相同的里程碑。

## 2. 角色

| 角色 | 做什么 | 不做什么 |
| --- | --- | --- |
| 决策人 | 定里程碑成果与截止日；批准协议变更和阶段门禁；派发执行 issue；合并 PR | — |
| 统筹方 | 架构设计与阶段计划；维护阶段与门禁；起草执行 issue 并建议执行方；验收；合并后补交付记录、关闭执行 issue | 不合并 PR；不改协议和已批准的设计；不替决策人放行门禁 |
| 执行方 | 只做 issue 写明的范围，交一个 PR 或一份测试记录 | 不扩范围；遇到停止条件时不猜 |

建议执行方时按任务性质分（具体名单写在项目文档里）：

| 任务性质 | 适合的执行方特点 |
| --- | --- |
| 架构设计、阶段计划、规范、ADR、接口头文件 | 擅长长上下文和设计的 agent |
| 跨模块或涉及契约的编码、需要实板的驱动与测试镜像 | 能读懂整个仓库、能操作台架的 agent |
| 边界清楚、只在主机上验证的编码：编解码、主机测试、小缺陷修复、工具脚本 | 便宜快速的 agent |
| 服务器部署、运维 | 有对应权限的 agent |
| 需要手工操作或仪器的实板测试 | 人 |

两条规则：

- **不自己验收自己。** 统筹方自己执行的 PR，按第 6.2 节自查并写进 PR，由另一个执行方交叉审核，最后由决策人合并。
- **开发与实板测试分成两个 issue**，即使由同一执行方完成。

## 3. 执行 issue 的写法

用模板 [exec-task.md](../assets/templates/exec-task.md)。要求：

- **自包含。** 执行方只能看到仓库和 issue。输入只列仓库内路径（必要时带提交号）或直接写在正文里；需要的数值连同来源抄进正文，不写“见聊天记录”或仓库外的文件。
- **范围写成目录。** “允许改动”和“允许新增”列出目录；其他目录一律视为范围外。只写功能描述时，执行方会顺手改周边代码。
- **完成定义可直接检验。** 数值带单位和条件，写明证据等级（L1 主机测试、L2 台架实测、L3 整机实测）。
- **规模有上限。** 一个 PR 应能一次读完。默认不含 vendor 代码约 1500 行以内，项目可以改。超过就拆。
- **标题** 写成 `[话题] 动宾短语`，话题沿用阶段 issue 的前缀。
- **不加没有依据的限制。** “范围外”只写目录、接口契约和项目已有规则。

## 4. 执行方须知

这一节写给执行方，起草时可以原样引用或由项目的 AGENTS.md 承担。

### 4.1 开始前

1. 读 issue 的“输入”，以及项目的 agent 说明、编码规范、测试指南。
2. 从 issue“起点”写明的提交建分支，分支名 `<执行方>/<issue 号>-<短名>`。

### 4.2 交付

- PR 正文写 `Refs #<issue 号>`，不写 `Closes`：issue 由统筹方在合并后关闭。
- PR 正文必须包含：执行过的验证（命令、结果摘要、证据等级）；未执行的验证和原因；与 issue 的偏离及原因。
- 改了受管理文件时，按项目的文控约定更新登记表（见 `/emb-repo:artifact-conventions`）。
- 交付后把 issue 标签改为 `status:review`。

### 4.3 停止条件

遇到以下情况，在 issue 里评论提问后等待，不猜也不绕过：

- 接口契约、协议字段或状态含义不清；
- 硬件行为未知，或与手册不一致；
- 需要改动范围外的文件，或需要改协议、接口定义；
- 规模明显超过上限。

## 5. 实板交付：可复用的进仓库，过程不进

需要实板证据（L2 及以上）的完成定义，单独开一个执行 issue，标 `needs:hw`：

- 开发 issue 交付测试镜像、测试脚本和操作步骤；
- 实板测试 issue 写明板与硬件版本、固件提交、接线、步骤、门槛（带单位）和要回传的数据；
- 统筹方对照门槛给出判定。不通过时开缺陷 issue，链接到本 issue。

开发 PR 在主机测试（L1）通过后可以先合入；对应的实板项在实板测试 issue 关闭前保持未勾选。

实板任务的产出分成两类，分开交付：

1. **可复用的东西**：测试镜像源码、主机脚本、台架工具的修复。下次谁都能照着复现。
   - 放在项目的正常目录（按画像第 5、7 节：板级测试镜像目录、工具目录、主机测试目录），带 README：接线、构建、怎么看结果。
   - 按普通代码 PR 交付，要有主机测试或构建证据，能直接合入。
   - 不放进压缩包、快照或记录目录。只在记录里出现的源码等于没有交付。
2. **证据**：一次实板运行一篇记录，用 [hw-record.md](../assets/templates/hw-record.md)，正文不超过一页。
   - 开头表格写清镜像：每个镜像一个 BIN SHA-256 和对应提交。
   - 正文只写：测了什么、关键数据（带单位）、判定、没覆盖什么、下一步。
   - 原始日志不提交仓库。需要留存时打成一个压缩包附在 issue 评论里，记录中写文件名和 SHA-256。

记录和 PR 正文不写以下内容：

- 台架资源占用与归还的时间线、会话编号、句柄或进程何时关闭；
- 附件逐个文件的 SHA 清单、编码和行尾检查结果、自查用的模型；
- 原片备份与恢复过程。恢复失败或板子状态有变化才写，一句话说明现状。

纯证据 PR（只有记录）合入或关闭由决策人决定；判定和结论同时写在实板测试 issue 里，issue 是结论的入口。

## 6. 验收

### 6.1 流程

1. 统筹方起草执行 issue，标 `status:draft`；决策人确认后改为 `status:ready`。
2. 决策人派发，打 `agent:<执行方>`。
3. 执行方交付后标 `status:review`，并通知统筹方。
4. 统筹方按第 6.2 节验收，能在主机上重跑的测试自己重跑。结论只有三种：通过、不通过、有条件通过（写明限制和确认人）。
   - PR 上评论缺什么、在哪里；
   - issue 上评论三行：“做了：”“结果：”“下一步：”。
5. 不通过：标 `status:changes`，执行方在同一个 PR 上修改，统筹方只复核变化部分。
6. 通过：决策人合并。PR 改动了已有代码或文档的，合并前请原作者复核。
7. 合并后统筹方填写“交付记录”，以“已完成”关闭执行 issue，勾选阶段 issue 中对应的完成定义；修改 issue 正文时，在下方评论说明改了什么。
8. 一个阶段的执行 issue 都已关闭、门禁证据齐全后，统筹方在阶段 issue 里写门禁检查（可以进入 / 有条件进入 / 不能进入），由决策人确认后关闭。

评审机器人的意见不自动视为缺陷：统筹方先评估并在 PR 上回复，由决策人决定是否修改。

### 6.2 验收清单

- [ ] **范围**：改动只在允许的目录内；没有无关重排；vendor 代码单独提交；规模在上限内。
- [ ] **完成定义**：每条都有证据，等级不低于要求；编译通过和主机测试不充当实板结果。
- [ ] **契约**：实现与接口头文件、规范章节一致；没有改协议或接口，需要改的已事先经决策人同意。
- [ ] **测试**：行为变化补了测试；统筹方重跑结果与 PR 所述一致。
- [ ] **门禁**：没有新增无依据的门禁、锁止、上限、拒绝路径；有的写明了来源和撤销条件。
- [ ] **文控**：受管理文件改动已更新登记表；没有改已取代或已归档的文件。
- [ ] **README**：`docs/` 以外的 README 在本目录内自包含。
- [ ] **数值来源**：寄存器、时序、容量、主频等数值有来源。
- [ ] **PR 正文**：有 `Refs #N`、执行过的验证、未执行的验证、与 issue 的偏离。
- [ ] **实板交付**：可复用的镜像和工具在正常目录、可合入；记录不超过一页，原始日志不进仓库（第 5 节）。

## 7. 标签

issue-tracking 的 `type:`、`area:`、`hw:`、`defect:` 标签不变。执行 issue 另用：

| 标签 | 含义 | 谁打 |
| --- | --- | --- |
| `exec` | 执行 issue | 统筹方 |
| `agent:<执行方>` | 当前执行方，例如 `agent:human` | 决策人派发时 |
| `needs:hw` | 实板测试 issue | 统筹方 |
| `status:draft` | 草稿，等决策人确认 | 统筹方 |
| `status:ready` | 可以派发 | 决策人 |
| `status:blocked` | 被阻塞，正文“依赖”写明在等什么 | 任何人 |
| `status:review` | 已交付，等验收 | 执行方 |
| `status:changes` | 验收未通过，等执行方修改 | 统筹方 |

这些标签须先在仓库中建好：GitHub 用网页模板新建 issue 时会忽略不存在的标签；用 API 加标签前也应先确认标签已存在。

与 issue-tracking 四个状态的对应：`ready` 与 `changes` 为待处理，`blocked` 为被阻塞，`review` 为待确认；关闭即已关闭。`status:` 标签只用于执行 issue。

## 8. 常见错误

| 错误 | 后果 | 改法 |
| --- | --- | --- |
| 输入写“按刚才讨论的方案” | 执行方看不到讨论，只能猜 | 把方案要点、数值和来源写进正文 |
| 范围只写功能，不写目录 | 执行方顺手重构周边代码，PR 变大、难审 | 列出允许改动和新增的目录 |
| 开发和实板测试一个 issue | 主机测试通过就勾了实板项 | 拆成两个，实板项在实板 issue 关闭前不勾 |
| 测试镜像源码只在附件压缩包里 | 下次无法复现，等于没交付 | 镜像源码放正常目录，按代码 PR 合入 |
| 记录写满占用时间线、逐文件哈希 | 读不到结论 | 一页：镜像、关键数据、判定、没覆盖、下一步 |
| 自己写的 PR 自己说通过 | 没有独立复核 | 交叉审核，决策人合并 |
| 评审机器人的每条意见都改 | PR 被带偏，甚至加入无依据的门禁 | 先评估，有依据的才改，涉及方向的交决策人 |
| PR 写 `Closes #N` | 合并即关闭，来不及补交付记录和勾阶段 | 写 `Refs #N`，统筹方合并后关闭 |
