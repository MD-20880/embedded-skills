# 嵌入式产品开发的 issue 管理方式

这是一种用 issue（或工单、工作项）管理嵌入式产品开发的方式。它适用于任何产品和任何工具，不绑定具体项目。

本方式分两层：

- **核心约定**（第 2 章）：只有五条，是这套方式成立的前提，建议不要改。
- **默认做法**（其余章节）：类型、字段、状态名、阶段、证据等级等，团队可以按自己的习惯调整。调整结果写在项目自己的文档里。

## 1. 要解决什么

嵌入式产品开发的 issue 有几个特有的难处：

- **结论只对特定对象成立。** 同一个测试，在 A 版板上通过，在 B 版板上可能不通过；换一版固件、换一个料号，结论也可能变。
- **改板有窗口期。** PCB 一旦冻结，硬件问题要等下一版。一个问题晚一周有结论，可能就要多等一轮改板。
- **大量 open issue 其实是“测一下够不够”。** 这类工作写成任务，复选框全勾上了，却说不出过没过。
- **证据的可信度差别很大。** 编译通过、仿真、开发板实测、整机实测、认证测试，常被混为“验证过了”。
- **缺陷不一定在本版修好。** 很多缺陷要等下一版硬件修，或者用软件规避，或者接受为已知限制，只靠“已修复/未修复”描述不了。
- **多方交叉。** 硬件、固件、结构、射频、工艺、供应商、认证机构，经常卡在团队外部。

这套方式的目标只有一个：**任何人打开一个 issue 或一张总览，都能一眼看出它完没完、卡在哪里、由谁拍板，以及离下一个开发阶段还差什么。**

## 2. 核心约定

1. **完没完要一眼可见。** 每类 issue 都有明确的完成标志：问题看答案，验证看判定，缺陷看处置结果，任务看验收。动作清单做完不算完成，因为动作只是手段。
2. **结论绑定对象。** 每个结论都写明适用于哪块板、哪个硬件版本、哪版固件、什么配置。换了对象，结论不自动沿用。
3. **不编造。** 门槛、负责人、日期、证据不知道时，写“待定”，并写明由谁、何时定。编造出来的门槛会让后面所有判断都失去依据。
4. **证据分等级。** 编译通过、仿真、计算不能冒充实测。结论写明证据等级（第 7 章）。
5. **一个 issue 只管一件事。** 多件事混在一起，就只能写“进行中”，永远说不清。

## 3. 四类 issue

| 类型 | 管什么 | 标题写法 | 怎样算完 |
| --- | --- | --- | --- |
| 问题 | 结论未知、会影响后续决定：选型、方案取舍、门槛定多少、不确定算不算错 | 是非类用“是否”；其余用“哪个 / 多少 / 什么” | 写出答案，决策人确认 |
| 验证 | 对照已知的规格或限值，判断某个对象是否达标 | “X 在 Y 条件下是否达到 Z” | 判定为通过或不通过，附证据；不通过就转成缺陷或问题 |
| 缺陷 | 期望明确，并且看到了与之不一致的现象，或按资料能确定是错的；原因可以还不知道 | 现象 | 按第 6.3 节的某种处置方式完成 |
| 任务 | 目标明确、做完就能直接验证的工作：写驱动、出测试固件、改版图、做工装 | 动宾短语 | 交付并通过验收 |

**拿不准时，按顺序问：**

1. 期望明确，并且看到了与之不一致的现象，或按资料能确定是错的？→ **缺陷**，原因不知道也算
2. 有现成的规格或限值，只需要测量对比？→ **验证**
3. 做完后不需要再判断，就能知道完成没有？→ **任务**
4. 其余情况，包括门槛还没定、要做选择、不确定算不算错 → **问题**

**问题和验证的区别**：验证的判据在开始时就已明确（限值来自规格书、器件手册或法规），只差测量；问题的答案本身还要靠判断或决策。门槛还没定的“验证”，实际上是一个问题（“门槛是多少”）加一个被它阻塞的验证。

**疑似有问题时，看有没有实测到的现象：**

| 情况 | 例子 | 算什么 |
| --- | --- | --- |
| 看到了现象，不知道原因 | 花屏、无声、偶发复位 | 缺陷，归属标“待查”，先定位再处置（第 5.3 节） |
| 没看到现象，按资料能确定是错的 | 分压接到了没有 ADC 功能的引脚 | 缺陷，直接定归属 |
| 没看到现象，只是担心有风险 | 某路电源可能超出器件额定值 | 验证；限值未定就先开问题。不通过再开缺陷 |
| 不确定算不算错 | 续航偏短，但没有门槛 | 问题：“门槛是多少” |

只是担心的风险不开成缺陷，否则缺陷列表会混进本来没问题的东西。

## 4. 共用字段

四类 issue 都带以下字段。可以用标签、项目字段或正文中的固定段落实现。

| 字段 | 内容 | 为什么需要 |
| --- | --- | --- |
| 适用对象 | 板名和硬件版本、固件版本、配置或装配差异（如单麦/双麦、某料号） | 结论只对特定对象成立 |
| 领域 | 硬件、固件、结构、射频、工艺、供应商、认证……（按团队自定义） | 找对负责人，按领域筛选 |
| 截止节点 | 必须在哪个阶段或节点之前完成，例如“DVT 改板冻结前” | 改板窗口有限，错过就要多等一轮 |
| 决策人 | 谁确认判据，谁确认结论 | 没有拍板人的问题永远关不了 |

## 5. 各类 issue 的写法

### 5.1 问题

| 段落 | 内容 |
| --- | --- |
| 标题 | 是非类写“对象 + 是否 + 期望状态或决定”；选择、数值、原因类写“哪个 / 多少 / 什么”。不加问号（第 15.1 节） |
| 为什么问 | 答案影响哪个决定；不回答会卡住什么 |
| 判据 | 怎样算答完：比较维度、门槛、方法、决策人。未知项写“待定，由谁在何时定” |
| 依赖 | 阻塞于谁，阻塞了谁 |
| 手段（可选） | 为取得答案要做的事，或挂上相关任务；不作为关闭条件 |
| 答案 | 结论、依据（链接到验证结果和数据）、适用对象、剩余限制、引出的新 issue，以及决策记录：谁、何时、基于什么定的 |

### 5.2 验证

| 段落 | 内容 |
| --- | --- |
| 标题 | “X 在 Y 条件下是否达到 Z”，Z 写期望状态，不加问号 |
| 依据 | 规格条目、器件手册、法规标准或需求编号 |
| 判据 | 限值、测量方法、测试条件（温度、电压、负载、样本数）、要求的证据等级 |
| 对象 | 板、版本、固件、样本编号 |
| 结果 | 单个对象写一行结论；多个对象或条件用结果表（第 9 章） |
| 判定 | 通过 / 不通过 / 有条件通过。有条件通过要写明限制，并由决策人确认 |
| 后续 | 不通过时，链接新开的缺陷或问题 |

### 5.3 缺陷

一个缺陷从发现到关闭分四步，始终是同一个 issue：

1. **现象**：记下复现步骤、环境和复现率。只出现过一次的，复现率写 1/N。
2. **定位**：查出根因，定下归属。
3. **处置**：选处置方式（第 6.3 节）并执行。根因确认之前不选处置方式。
4. **复测**：通过后关闭。

**归属**指缺陷出在哪里：

| 归属 | 范围 | 标签 |
| --- | --- | --- |
| 待查 | 还没定位 | `defect:tbd` |
| 硬件缺陷 | 原理图、PCB、BOM、器件选型、装配与焊接、结构 | `defect:hw` |
| 软件缺陷 | 固件、驱动、协议和软件设计文档、配置、上位机、App、云端 | `defect:sw` |

定位的规则：

1. **归类就是定位的结论。** 换标签的同时，在“定位”段写明根因和证据等级。只换标签、不写根因，不算定位完成。
2. **由缺陷的负责人定位。** 还没有负责人的，在复核时指派。
3. **按根因定归属，不按修法定。** 根因在硬件、用软件绕开的，仍是硬件缺陷，处置为“软件规避”。
4. **硬件和软件都要改才能修好时，拆成两个缺陷**，互相链接。
5. **定位工作量大时**，例如要做几组实验或几个人分头查，在缺陷下挂验证或任务作为子 issue。
6. **查完发现不是缺陷的**，按第 6.2 节以“符合预期”“无法复现”或“重复”关闭。

硬件缺陷另有两条：

- **分设计缺陷和个体缺陷。** 设计缺陷出现在同一版本的每块板上。个体缺陷只出现在指定板号上，例如虚焊、装错料、器件批次问题；要写明板号，并标明在这块板上得出的其他结论是否受影响。同一个个体问题在多块板上出现时，改按设计或工艺问题处理。
- **截止节点**写计划修复它的那一版的改板冻结点。

三种归属用同一个模板（`assets/templates/defect.md`），开缺陷时就用它，定位后不换模板。现象、期望、影响三段在定位前就要写。定位后补齐其余各段，并删掉不适用的行：

- 硬件缺陷多写：设计缺陷还是个体缺陷；位号、网络名、设计值和实装值；受影响的板号；现有样板怎么处理（返修、飞线、停用，或照用并注明）；原理图和 BOM 的更正。复测在目标硬件版本上做。
- 软件缺陷多写：固件版本范围和提交号；引入问题的版本或提交（知道才写）；修复的提交或 PR；是否加了回归测试。

### 5.4 任务

| 段落 | 内容 |
| --- | --- |
| 标题 | 动宾短语，说清交付什么 |
| 目标 | 服务于哪个问题、验证或阶段目标 |
| 完成定义 | 可直接验证的条件：产出物、验收方法、通过标准 |
| 范围外 | 明确不做的部分 |
| 交付记录 | 产出链接、验收结果 |

## 6. 状态与关闭方式

### 6.1 四个状态

| 状态 | 含义 |
| --- | --- |
| 待处理 | 还没完成，可以推进或正在推进 |
| 被阻塞 | 在等别的东西；写明在等什么，并区分**内部**（另一个 issue）和**外部**（供应商、原厂、认证机构、新一版硬件到货） |
| 待确认 | 答案、判定或修复已经完成，等决策人确认或复测 |
| 已关闭 | 写明关闭方式（第 6.2、6.3 节） |

“进行中”不单设状态，看负责人和最近的更新即可。状态少，维护时出错就少。

### 6.2 一般关闭方式

| 方式 | 适用 |
| --- | --- |
| 已回答 | 问题 |
| 通过 / 不通过 / 有条件通过 | 验证。“不通过”同样是结论，同样关闭，并链接后续 issue |
| 已完成 | 任务 |
| 不再需要 | 背景变化，结论已不影响任何决定；写明原因 |
| 重复 | 链接保留的那个 issue |
| 符合预期 | 缺陷：查完发现行为本来就对；写明依据 |
| 无法复现 | 缺陷：写明试了多少次、在什么条件下 |
| 已拆分 | 链接全部子 issue |

### 6.3 缺陷的处置方式

| 处置 | 用于 | 何时可以关闭 |
| --- | --- | --- |
| 固件修复 | 软件缺陷 | 修复已合入，并在受影响对象上复测通过 |
| 改板修复 | 硬件缺陷 | 在目标硬件版本上复测通过。新板到货前，状态为“被阻塞（外部：等新版本硬件）”，不要提前关闭 |
| 软件规避 | 硬件缺陷、软件缺陷 | 规避已合入并复测；剩余风险写入已知限制清单。用于硬件缺陷时，还要写明下一版是否改板 |
| 接受限制 | 硬件缺陷、软件缺陷 | 决策人确认放行，并写入已知限制清单（含适用版本和对用户的影响） |

硬件缺陷先用软件规避、下一版再改板时，处置写“改板修复”，规避作为临时措施写在“影响”段。这样它在新板复测通过前一直保持打开。

## 7. 证据等级

默认分五级，团队可以调整名称和划分方式：

| 等级 | 证据 | 典型例子 |
| --- | --- | --- |
| L0 | 推断与资料 | 器件手册、计算、经验判断 |
| L1 | 仿真与主机测试 | 电路仿真、单元测试、编译通过 |
| L2 | 台架实测 | 开发板或裸板，仪器测量 |
| L3 | 整机实测 | 装壳、目标环境、实际使用姿态 |
| L4 | 认证与第三方测试 | 认证实验室、客户验收 |

用法：

- 每个答案、判定和复测结果，都写明证据等级和对应的对象（板号、版本、固件）。
- 验证的判据中写明要求的最低等级。等级不够的结果，只能算“初步结论”，不能据此判定通过。
- 证据要能被别人重新查看：数据、波形、截图、日志、测试记录的链接。“测过了没问题”不算证据。

## 8. 开发阶段与截止节点

默认阶段：

| 阶段 | 关注点 | 证据等级的通常要求 |
| --- | --- | --- |
| EVT（工程验证） | 原理和关键功能可行；关键选型有结论 | 关键项 L2 |
| DVT（设计验证） | 设计满足全部规格，包括环境、可靠性和认证预测试 | L3；认证相关项建议预测试 |
| PVT（生产验证） | 产线工艺、良率、测试工装、试产批次 | 试产批次上的 L3 |
| MP（量产） | 稳定量产 | 认证项 L4 |

截止节点可以比阶段更细，例如“EVT 改板冻结”“DVT 开模前”。规则：

- 每个 issue 都写截止节点。不写的，在总览里列为“需要补齐”。
- 需要改板才能解决的问题和缺陷，截止节点应早于对应阶段的改板冻结点。
- 一个阶段结束前，截止节点在该阶段的 issue 要么已关闭，要么在阶段门禁检查（第 11 章）中被明确放行。

## 9. 验证矩阵怎样拆

一个规格项常常要在多个板版本、多个温度点或多个样本上验证。

**放在一个 issue 里，用结果表**，当以下条件都满足时：

- 方法相同；
- 决策人相同；
- 预计一起完成，没有各自不同的阻塞。

结果表示例：

| 对象 | 条件 | 结果 | 判定 | 证据 |
| --- | --- | --- | --- | --- |
| 板 B 版 #3，固件 0.4 | −20 °C | 20/20 次启动成功，最慢 2.1 s | 通过 | 链接 |
| 板 B 版 #3，固件 0.4 | 60 °C | 待测 | — | — |

全部行都有判定后，整个 issue 才判定。任何一行不通过，就开缺陷或问题并链接，整体判定为不通过或有条件通过。

**拆成多个 issue**，当出现以下任一情况时：

- 不同对象或条件的阻塞不同（例如某个温度点要等温箱，某个版本要等新板）；
- 负责人或决策人不同；
- 截止节点不同。

## 10. 总览的三种视图

总览只列问题、验证和缺陷；任务挂在它们下面，不单独列。

| 视图 | 回答什么 | 分组方式 |
| --- | --- | --- |
| 按状态 | 现在卡在哪里 | 被阻塞（内部 / 外部）、待定位、待确认、待处理、需要补齐、本期已关闭 |
| 按截止节点 | 离下一个阶段还差什么 | 按 EVT / DVT / PVT / MP 及更细的节点分组，每组列未关闭项 |
| 按对象 | 某块板、某个版本还有哪些问题 | 按板名和版本分组 |

“需要补齐”一组单独列出缺适用对象、缺截止节点、缺判据、缺决策人的 issue，这些就是下一步要做的事。

“待定位”一组列出归属还是待查的缺陷，写明负责人和开了多久。放了很久没人查的，复核时优先处理。

按对象视图中，硬件缺陷按板名和硬件版本分组，软件缺陷按固件版本分组，待定位的缺陷列在发现它的板和固件下。按截止节点视图中，硬件缺陷列在对应的改板冻结点下。

建议每周复核一次（节奏由团队定）。复核只做三件事：确认“待确认”的项；处理阻塞，尤其是外部阻塞；补齐缺失的字段。

### 10.1 个人热点

总览回答“项目卡在哪里”，个人热点回答“我最近在跟什么”：把某人近期参与最多的 open issue 排到前面，用来快速回到自己的焦点上。它是个人的辅助视图，不替代总览，也不改变任何 issue 的状态。

打分只看事件，不看 issue 的“最近更新时间”。批量改标签、改模板会刷新更新时间，按它排会把一大批没人动过的 issue 顶上来。

窗口内（默认 14 天）每个事件按“权重 × 0.5^(距今天数 / 半衰期)”累加，半衰期默认 3 天：

| 事件 | 权重 |
| --- | --- |
| 本人的 PR 引用该 issue | 4 |
| 本人新开、本人评论 | 3 |
| 本人的提交引用该 issue、指派给本人、他人评论中 @本人 | 2 |
| 他人评论、他人的 PR 引用该 issue | 1 |
| 当前指派给本人（不衰减） | 1 |

本人相关得分大于 0 的列入“我的热点”；其余按总分取前几名，单列为“团队热点”，供参考。权重是默认值，团队可以调整，调整后写进项目自己的文档。

## 11. 阶段门禁检查

回答“能不能进入下一阶段”。检查范围：截止节点在当前阶段及以前的全部 issue。

逐项核对：

1. 未关闭的问题、验证和缺陷，各有多少，分别是哪些；其中还没定位的缺陷单独列出。
2. 已关闭项中，证据等级低于本阶段要求的有哪些。
3. 以“有条件通过”“软件规避”“接受限制”关闭的项，是否都已写入已知限制清单并经决策人确认；其中以软件规避关闭的硬件缺陷，下一版是否改板是否已有决定。
4. 要靠改板解决、但已错过本阶段改板冻结点的硬件缺陷和问题有哪些，计划在哪一版解决。

输出：

```text
结论：可以进入 / 有条件进入 / 不能进入
未关闭：……（编号、标题、卡在哪里）
证据不足：……
已知限制：……
需要决定：……（例如：是否带着某缺陷进入 DVT；由谁定）
```

门禁本身也是一个问题（“是否可以进入 DVT”），用问题类 issue 记录答案和决策。

## 12. 常见错误

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 关闭条件写成动作 | 动作做完了，仍没有结论 | 关闭条件写成答案、判定、处置或验收；动作放进“手段” |
| 验证没有限值 | 测完也判不了 | 写出限值；限值未定就先开“门槛定多少”的问题 |
| 结论不写对象 | 换版后误用旧结论 | 写明板、版本、固件、配置 |
| 拿开发板结论当整机结论 | 装壳后才发现问题 | 写明证据等级，门禁按等级检查 |
| 改板修复的缺陷提前关闭 | 新板上问题仍在却没人跟 | 新板复测通过才关闭；之前保持“被阻塞（等新版本硬件）” |
| 根因没确认就动手修 | 修错地方 | 先定位：写出根因和归属，再选处置方式 |
| 按修法定缺陷归属 | 硬件问题用软件绕开后关闭，下一版没人改板 | 按根因定归属；用软件规避的硬件缺陷，写明下一版是否改板 |
| 一个 issue 装多件事 | 状态说不清 | 拆分 |
| 答案只在评论里 | 后来的人找不到 | 写进答案或判定段 |
| 编造门槛或负责人 | 后续判断全部失去依据 | 写“待定，由谁在何时定” |

## 13. 落地与迁移

### 13.1 落地到工具

只需要工具支持以下能力：

| 能力 | 常见实现方式 |
| --- | --- |
| 类型 | 标签 `type:question` / `type:verification` / `type:defect` / `type:task`，或工具自带的类型；缺陷另加归属标签 `defect:tbd` / `defect:hw` / `defect:sw` |
| 状态 | 标签、看板列或项目字段 |
| 共用字段 | 标签（如 `area:power`、`hw:B`、`gate:DVT`）、项目字段，或正文中的固定段落 |
| 关联与依赖 | 父子 issue、阻塞关系或正文链接（见第 14 章） |
| 模板 | issue 表单或正文模板 |
| 总览 | 看板或表格视图，或一个手工维护的总览 issue |

项目已有自己的标签或字段时，做一张映射表放进项目文档，不必改名。

### 13.2 迁移现有 issue

1. **盘点**：逐个阅读现有 issue，找出其中包含的问题、验证、缺陷和任务。一个旧 issue 常常四类都有。
2. **出改写方案**：列出每个旧 issue 拆出的新 issue，写明类型、标题、判据（或“待定，由谁定”）、适用对象、截止节点和依赖。
3. **评审**：由项目负责人确认方案。未经确认，不改动别人创建的 issue。
4. **执行**：
   - 只含一件事的，就地改写，保留历史；
   - 需要拆分的，按第 14 章处理：优先把原 issue 改写成父 issue，新开的子 issue 挂在下面，标题加话题前缀；原 issue 不适合做父 issue 时，才以“已拆分”关闭并链接全部新 issue；
   - 旧讨论中已有的结论，写进对应 issue 的答案或结果，并链接原讨论。
5. **建总览**：按第 10 章的三种视图汇总。

## 14. 关联与标签

issue 之间有两种关联，分别用不同的方式表达：

| 关联 | 例子 | 怎样表达 |
| --- | --- | --- |
| **同源**：同一个话题当场产生的一组 issue | 一个大 issue 拆出的几个验证 | 标题前缀 `[话题]`，加一个父 issue |
| **事后串联**：后来才认识到的关联 | 几个现象最后查到同一个根因；零散的低温相关 issue | 标签；根因关联用链接 |

规则：

1. **标题写成 `[话题] 问题本身`。** 前缀只写出身话题，一个 issue 只有一个话题，用短名。没有所属话题的 issue 不加前缀。出身是创建时就确定的事实，以后不会变，所以可以放在标题里。
2. **会变的东西不放标题。** 类型、状态、优先级、阶段、板和版本，都用标签或字段表示。
3. **同源的一组有一个父 issue。** 父 issue 通常就是这个话题要回答的问题，例如“X 是否需要改板”。拆分时，原 issue 可以就地改写成父 issue，把子 issue 挂在下面；原 issue 不适合做父 issue 时，才以“已拆分”关闭。
4. **标签分组管理，数量要少。** 默认四组：`type:`、`area:`、`hw:`、`gate:`。缺陷另有一组归属标签 `defect:tbd`、`defect:hw`、`defect:sw`；注意 `hw:` 标的是板和硬件版本，`defect:hw` 标的是缺陷归属，两者不同。临时主题用 `theme:`，在复核时打上，主题结束后撤掉。
5. **根因用链接，不用标签。** 例如写“根因见 #X”。标签只能说明“有关”，链接能说明“因为什么”。阻塞关系写在“依赖”里，同样不用标签。
6. **临时主题变大了，就升级为话题**：新开一个父 issue，把相关 issue 挂上去。已有 issue 的标题不改，以便搜索。

## 15. 写作风格

目标：扫一眼就能读懂，读完不会产生两种理解。

### 15.1 标题

| 类别 | 形式 | 例子 |
| --- | --- | --- |
| 是非类：验证，以及要做决定的问题 | `[话题]` 对象 + 是否 + 期望状态或决定 | [电源低温] 主板 B 版在 −20 °C 下冷启动是否 20 次全部在 3 s 内成功 |
| 选择、数值、原因类问题 | `[话题]` 用“哪个 / 多少 / 什么” | [电源低温] 低温续航门槛是多少 |
| 缺陷 | `[话题]` 现象 | 硬件：[电源低温] −20 °C 下 3V3 上电过冲超过 MCU 额定值<br>软件：[电源低温] −20 °C 下看门狗在初始化完成前复位 |
| 任务 | `[话题]` 动宾短语 | [电源低温] 搭建可编程低温测试环境 |

- 标题不加问号。“是否”“多少”这类词已经表明它是待回答的。
- “是否”后面接期望成立的状态，例如写“是否在额定范围内”，不写“是否超出额定”。这样答案“是”就等于通过。
- 不用“确认”“核实”“梳理”“推进”“调研”这类动作词开头。

### 15.2 正文

1. **一句只说一件事。** 长句拆开，或者改成列表。
2. **事实、推断、待查分开标。** 每条用固定标记开头：“实测（L2）：”“推断：”“待查：”。推断相当于证据等级 L0；实测要写明等级。
3. **写能检验的话。** 数值带单位和条件，例如“≤ 50 mVpp（满载，20 MHz 带宽）”。不写“偏高”“足够”“稳定”“尽快”“满足要求”。
4. **写明谁来做。** 写“硬件负责人在测量前补齐限值”，不写“需补齐限值”。
5. **不用管理套话。** “收敛”“闭环”“推进”“落实”“对齐”“充分”“有效”这类词，换成具体的动作或结果；有具体说法时，通常直接删掉。
6. **不复制样板。** 每个 issue 都适用的要求，放在本方式和模板里；正文只写这个 issue 特有的内容。
7. **同一个东西始终用同一个名字。** 首次出现时写成“引脚名（网络名）”，之后保持一致。优先用原理图上的网络名和引脚名。
8. **并列关系写清楚。** 写明是“和”还是“或”，不用“／”连接。
9. **进展评论分三行**：“做了：”“结果：”“下一步：”。

### 15.3 示例

改前：

> 传感器 INT 线可能经 R12 接到 5 V 域，需确认实物连通性／电平兼容和引脚耐压；高阻不等于隔离；以上均需实测，不据此直接认定 MCU 已损坏。

改后：

> **推断：** 传感器的 INT 线可能经 R12 接到 5 V 域（来源：原理图第 3 页）。
> **待查：** 实物是否连通；MCU 该引脚的耐压。由硬件负责人确认。
> **注意：** 引脚设为高阻，不能隔离外部电压。
> 目前没有实测数据，不能认定 MCU 已损坏。

## 16. 术语

| 术语 | 含义 |
| --- | --- |
| 判据 | 判断是否完成的标准：限值、方法、条件、证据等级、决策人 |
| 适用对象 | 结论成立的板、硬件版本、固件版本、配置 |
| 截止节点 | 必须在其之前完成的开发阶段或节点 |
| 证据等级 | 证据的可信度级别，默认分 L0 到 L4 |
| 决策人 | 有权确认判据和结论的人 |
| 缺陷归属 | 缺陷出在硬件还是软件，按根因定，不按修法定；定位前为待查 |
| 定位 | 查出缺陷的根因并定下归属 |
| 已知限制清单 | 带着进入下一阶段或发布的限制，包括适用版本和影响 |
| 手段 | 为完成 issue 而做的事，不作为关闭条件 |
